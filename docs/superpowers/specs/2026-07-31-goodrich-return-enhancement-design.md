## 1. 문제

Goodrich 펀드매니저의 랭킹 함수가 알파를 뒤집고 있다.

`C:\GoodrichTradingOS\services\api\src\goodrich\fund_manager.py::_score`:

```python
score = 50 + range_position * 25 + momentum * 0.8 + liquidity * 20
#            당일 고저 대비 위치    당일 등락률      거래대금
```

**당일 스냅샷 하나만** 사용한다. 다일 가격 이력·상대강도·수급·업종 정보가 전혀 없다.
구조적으로 "오늘 이미 많이 올랐고 고가 근처인 종목"을 1위로 뽑는다.

### 1.1 실측 (원장 48행, T+1 n=36, 벤치마크·비용 반영)

| 지표 | 값 |
|---|---|
| corr(점수, T+1 초과수익) | **−0.623** (원수익률 기준 −0.530) |
| 점수 <75 (n=20) | 평균 초과수익 **+2.94%** |
| 점수 ≥75 (n=16) | 평균 초과수익 **−5.09%** |
| 전체 초과수익 승률 | 61.1% |

**후보 유니버스에는 알파가 있는데 랭킹이 그것을 정확히 뒤집는다.**
점수 1위 에스피지(100.56) −4.35%, 3위 코스모로보틱스(98.42) **−20.37%**.

### 1.2 부수 발견

| 항목 | 값 |
|---|---|
| LLM 판정별 T+1 초과수익 | `BUY_CANDIDATE` n=2 → **+7.66%** / `WATCH` n=34 → −1.12% |
| 게시 픽 구성 | **94%가 WATCH** — LLM이 관망하라는 종목을 게시 중 |
| 벤치마크 정합성 | 원장 `market` 필드 **0/48 미기록** → 코스닥 종목도 KOSPI 지수로 비교 |
| 보유기간 정합성 | 30분 교체 주기 vs 목표가 +12~14% — 양립 불가 |

### 1.3 외부 근거

한국 시장 1983~2023 연구: **개별종목 모멘텀에서 반전 효과가 지배적**. 산업 모멘텀은 유의하지
않으며, 개별종목 반전은 산업 모멘텀을 통제해도 유지된다. 단 유니버스를 KOSPI200으로 좁히면
모멘텀이 유의해진다 — 유니버스 선택이 결과를 뒤집는다.

현 `_score`는 문헌이 "한국 개별종목에서 지는 축"이라고 지목한 바로 그 축(당일 상승폭 +
고가 근접)에 100% 베팅하고 있다.

## 2. 목표

Goodrich가 "이미 오른 종목"이 아니라 "앞으로 오를 종목"을 고르게 한다.
성패는 **벤치마크 초과수익(왕복 비용 반영)** 하나로만 판정한다.

기존 측정 하네스(`goodrich_ledger.py`)가 이 기준을 이미 구현하고 있다 —
look-ahead 차단, 날짜 정렬 벤치마크, 비용률 반환, pending≠0% 원칙.

### 2.1 확정된 제품 결정

1. **두 제품을 분리 제공한다** — "오늘의 포트폴리오(D+N 보유)"와 "장중 관심종목(30분 갱신)"
2. **랭킹은 MarketFlow가 소유한다** — Goodrich에는 순위가 붙은 후보를 전달
3. **확신 없는 날은 비운다** — 등급을 나눠 표시하되 기준 미달이면 그 자리를 채우지 않는다

## 3. 아키텍처

```
[MarketFlow]                                  [GoodrichTradingOS]

kis_screener (라이브 후보)
      ↓
goodrich_ranker (신규)  ←── 신호 라이브러리
      ↓ 순위·등급 붙은 후보 목록
      ├──── POST /v1/fund-manager/research ────→  수신 순서 그대로 사용
      │                                            (_score 정렬 제거)
      ←──── TOP3 + 등급 ──────────────────────────
      ↓
goodrich_ledger (기존) ──→ 원장 (append-only)
      ↑
백테스트 하네스 (신규) ←── daily_prices.csv 2년
```

랭킹 책임이 MarketFlow 한 곳으로 모인다. Goodrich는 실행·표시 계층이 된다.

**이 배치를 택한 이유**: 2년치 가격 이력·RS 등급·수급·VCP 데이터와 측정 하네스가 전부
MarketFlow에 있고, MarketFlow는 git·테스트로 보호된다. GoodrichTradingOS는 git 미관리라
로직을 두면 롤백이 불가능하다.

## 4. Phase 구성

각 Phase는 독립적으로 가치를 낸다. 앞 Phase가 실패하면 뒤로 진행하지 않는다.

| Phase | 산출물 | 독립 가치 |
|---|---|---|
| **1. 백테스트 하네스** | 유니버스 재현 + 신호 라이브러리 + 평가 엔진 | 이후 모든 판단의 근거. 이것만으로 "무엇이 되는지" 답이 나옴 |
| **2. 랭킹 후보 비교** | 현행 `_score` 포함 N개 함수를 동일 조건에서 비교 → 승자 선정 | 추측이 아닌 선택 |
| **3. 프로덕션 반영** | `goodrich_ranker` + 계약 확장 + 2제품 분리 + 등급 UI | 사용자에게 실제 전달 |
| **4. 라이브 A/B** | 원장 기반 사전/사후 비교 | 개선인지 개악인지 확정 |

## 5. Phase 1 — 백테스트 하네스

### 5.1 파일 구조

신규 패키지 `app/services/mirofish/goodrich_backtest/`:

| 파일 | 책임 |
|---|---|
| `universe.py` | 과거 날짜의 후보 유니버스 재현 |
| `signals.py` | look-ahead safe 신호 계산 |
| `rankers.py` | 비교 대상 랭킹 함수들 (현행 `_score` 포함) |
| `engine.py` | 랭킹 → TOP3 → T+N 초과수익 집계 |

각 파일은 하나의 책임만 가지며 독립적으로 테스트 가능하다.

### 5.2 유니버스 재현 (`universe.py`)

KIS 스크리너는 세 개 순위 API를 사용한다:

| KIS 소스 | 일봉 재현 방식 |
|---|---|
| `fetch_volume_rank(token, "3")` 거래대금 순위 | `current_price × volume` 상위 N |
| `fetch_fluctuation_rank(token)` 등락률 순위 | `change_rate` 상위 N |
| `fetch_volume_rank(token, "1")` 거래량 급증 | `volume / 20일 평균거래량` 상위 N |

세 집합의 합집합에서 `change_pct > 0` 필터(현행 `goodrich_client` 규칙)를 적용해 후보 풀을 만든다.

**인터페이스**:
```python
def reconstruct_universe(date: str, prices: PriceHistory, *, per_source_top_n: int = 30) -> list[Candidate]
```

`per_source_top_n`은 **소스별** 상위 N이며, 세 소스의 합집합이 후보 풀이 된다
(중복 제거 후 크기는 30~90 사이). 라이브 스크리너가 각 순위 API에서 상위권을 받아
합치는 구조와 동일하게 맞춘 것이다.

**재현 오차**: 라이브 스크리너는 장중 스냅샷 기준이고 재현은 종가 기준이다.
- "오늘의 포트폴리오"(장 시작 전 확정, D-1 종가 기반)는 **오차 없음** — 오히려 종가 기준이 정합
- "장중 관심종목"은 오차가 존재하므로 별도 취급하고, Phase 2에서 오차 크기를 측정해 명시한다

### 5.3 신호 라이브러리 (`signals.py`)

**look-ahead 금지 원칙**: 진입일 D의 랭킹은 **D-1 종가까지의 데이터만** 사용한다.
이 규칙은 단위 테스트로 강제한다 (미래 세션을 주입했을 때 결과가 바뀌지 않아야 함).

| 신호 | 정의 | 채택 근거 |
|---|---|---|
| `rs_rating` | O'Neil 12개월 가중 상대강도 (1~99) | 이미 구축·매일 갱신. 3~12개월 모멘텀은 유효 구간 |
| `pullback_depth` | 최근 20/60일 고점 대비 하락률 | 반전 효과의 반대편 — "이미 오른 것" 회피 |
| `flow_persistence` | 외국인·기관 5일/20일 순매수 연속성 | `all_institutional_trend_data.csv`로 이미 수집 중 |
| `volatility_norm` | ATR(14) / 종가 | 코스모로보틱스형(−20%) 폭탄 회피 |
| `liquidity` | 거래대금 로그 스케일 | 체결 가능성 |
| `overheat` | 당일·최근 3일 상승폭 | **현 문제항을 음의 가중(페널티)으로 전환** |

각 신호는 순수 함수로 구현하며, 입력은 D-1까지의 가격/수급 데이터, 출력은 정규화된 스칼라다.

### 5.4 평가 엔진 (`engine.py`)

기존 `goodrich_ledger.evaluate_pick`을 **재사용**한다 — look-ahead 차단·날짜 정렬 벤치마크·
비용 반영 로직이 이미 검증되어 있으므로 중복 구현하지 않는다.

```python
def backtest(ranker: Ranker, dates: list[str], *, top_k: int = 3,
             horizons: tuple[int, ...] = (1, 3, 5, 20)) -> BacktestResult
```

산출: 호라이즌별 평균/중앙값 초과수익, 승률, corr(점수, 초과수익), 진입일 수, 표본 수.

**벤치마크 정합성 수정**: 재현된 후보에는 시장 구분(KOSPI/KOSDAQ)을 부여해
`goodrich_ledger.benchmark_ticker`가 올바른 지수를 고르게 한다. 이는 1.2절의
"코스닥 종목도 KOSPI로 비교" 결함을 백테스트에서 반복하지 않기 위함이다.

## 6. Phase 2 — 랭킹 후보 비교

### 6.1 비교 대상

| 랭커 | 구성 |
|---|---|
| `baseline_current` | 현행 `_score` 그대로 (재구현) — **반드시 포함**. 개선 주장의 기준선 |
| `rs_led` | RS 등급 주도 + 유동성 필터 |
| `pullback` | 눌림목 깊이 주도 + RS 하한 |
| `flow_led` | 수급 연속성 주도 + 변동성 상한 |
| `composite` | 위 신호들의 가중 결합 |

### 6.2 과적합 방지

- **시간 분할**: 앞 구간에서 후보를 좁히고, 뒤 구간(holdout)에서만 최종 비교한다
- **단순 함수 선호**: 파라미터 수가 적은 쪽을 동률에서 우선한다
- **레짐 확인**: 상승·하락·횡보 구간별 성과를 함께 보고한다 (현 표본이 급락 국면 1회뿐이었던 한계 반복 방지)

### 6.3 성공 기준 (정량)

| 지표 | 현재 | Phase 2 통과 조건 |
|---|---|---|
| corr(점수, T+1 초과수익) | **−0.623** | **≥ 0** |
| T+3 평균 초과수익 | 미측정 | baseline 대비 개선 |
| T+5 평균 초과수익 | 미측정 | baseline 대비 개선 |
| 백테스트 진입일 | — | **200일 이상** |

**미달 시 Phase 3으로 진행하지 않는다.** 그 경우 산출물은 "현 신호로는 개선이 확인되지 않음"이라는
측정 결과이며, 이는 잘못된 변경을 프로덕션에 넣지 않았다는 점에서 유효한 결과다.

## 7. Phase 3 — 프로덕션 반영

### 7.1 랭커 (`app/services/mirofish/goodrich_ranker.py`)

Phase 2 승자를 구현한다. 백테스트의 `rankers.py`와 **동일한 신호 함수를 import** 하여
백테스트와 프로덕션이 갈라질 수 없게 한다 (recovery-leader 결함의 재발 방지 —
그 결함의 원인이 두 곳에 게이트가 따로 있었던 것이다).

```python
def rank_candidates(rows: list[dict], *, as_of: str) -> list[RankedCandidate]
```

- 킬스위치: `GOODRICH_RANKER_DISABLED=1` → 기존 동작으로 즉시 회귀
- 실패 시 폴백: 예외를 격리하고 순위 없는 목록을 반환한다 — **게시를 중단시키지 않는다**

### 7.2 계약 확장

현행: `detected_universe: dict[symbol -> name]`
확장: `ranked_candidates: [{symbol, name, rank, score, tier}]`

Goodrich 측 변경은 **최소**로 한다:
- `run_research_cycle`이 `ranked_candidates`를 받으면 `_score` 정렬을 건너뛰고 수신 순서를 사용
- 없으면 기존 `_score` 경로 유지 (하위호환)

GoodrichTradingOS는 git 미관리이므로 **수정 전 해당 파일을 백업**하고, MarketFlow 측에
계약 테스트를 둔다.

### 7.3 2제품 분리

| | 오늘의 포트폴리오 | 장중 관심종목 |
|---|---|---|
| 확정 시점 | 하루 1회, 장 시작 전 | 30분 갱신 (현행 유지) |
| 데이터 기준 | D-1 종가 | 장중 스냅샷 |
| 보유 전제 | D+3~D+20 | 당일~T+1 |
| 목표/손절 밴드 | 보유기간에 맞춘 밴드 | 장중 밴드 (+2~3%) |

현재의 "30분 교체 + 목표 +12~14%" 모순이 해소된다.

### 7.4 등급 표시

- **매수 확신** — 랭킹 상위 ∧ LLM 판정이 `BUY_CANDIDATE`·`BUY`·`STRONG_BUY` 중 하나
  ∧ 기존 profit/trend 게이트 통과. **3개 미만이면 그만큼만 표시하고 빈자리를 채우지 않는다**
- **관찰** — 나머지 상위 후보(`WATCH` 포함). "관찰" 라벨을 명시해 추천과 구분

1.2절에서 확인된 대로 LLM 판정은 표본이 작지만 방향이 맞다(BUY +7.66% vs WATCH −1.12%).
현재는 이 신호를 무시하고 94%를 WATCH로 게시하고 있으므로, 등급 분리는 그 자체로 개선이다.

## 8. Phase 4 — 라이브 A/B

원장(`goodrich_ledger.jsonl`)은 append-only이며 교체가 기록을 지우지 못한다.
Phase 3 배포 전후 구간을 같은 평가 코드로 비교한다.

- 판정 지표: T+3 평균 초과수익(비용 반영)
- 최소 관찰: 진입일 20일 이상 축적 후 판정
- 악화 시: 킬스위치로 즉시 회귀 후 원인 분석

원장에 `market` 필드를 기록하도록 수정한다(현재 0/48) — 코스닥 종목이 KOSPI 지수로
비교되는 현 상태로는 라이브 판정 자체가 왜곡된다.

## 9. 테스트

| 대상 | 방식 |
|---|---|
| 신호 함수 | 순수 함수 단위 테스트 + **look-ahead 회귀 테스트**(미래 세션 주입 시 결과 불변) |
| 유니버스 재현 | 알려진 날짜에 대해 실제 스크리너 결과와 겹침률 측정 |
| 랭커 | 결정성(같은 입력 → 같은 순위), 킬스위치, 폴백 경로 |
| 계약 | `ranked_candidates` 유/무 양쪽에서 Goodrich 응답 정상 |
| 회귀 | 기존 Goodrich 테스트 스위트 전체 통과 |

## 10. 위험과 완화

| 위험 | 완화 |
|---|---|
| 유니버스 재현 오차 (장중 순위 vs 종가) | D+N 제품은 종가 기준이라 정합. 장중 제품은 별도 취급 + 겹침률 측정 후 명시 |
| **GoodrichTradingOS git 미관리** | 수정 전 파일 백업, 변경을 정렬 부분으로 최소화, MarketFlow에 계약 테스트 |
| 과적합 | 시간 분할(학습/holdout), 단순 함수 선호, 레짐별 성과 병기 |
| 랭커 장애로 게시 중단 | 예외 격리 + 순위 없는 목록 폴백 + env 킬스위치 |
| 백테스트와 프로덕션 로직 분기 | 신호 함수를 **단일 모듈에서 양쪽이 import** (recovery-leader 결함 재발 방지) |
| 표본 부족한 LLM 신호 과신 | 등급 분리에만 사용하고 랭킹 점수에는 넣지 않는다. 표본 축적 후 재평가 |
