# 예측 리그(Forecast League) 설계

- 작성일: 2026-11-12
- 상태: 사용자 승인 대기 (설계 1~3부 구두 승인 완료)
- 상위 문서: `docs/superpowers/specs/2026-08-24-goal-definition-master-plan.md` (충돌 시 상위 문서 우선. 단, 본 문서 §2의 결정은 2026-11-11~12에 사용자가 새로 확정한 것)

## 1. 배경

2026-11-11에 앱 전체를 다섯 영역(백엔드, 프론트엔드, AI 파이프라인, 보안, 기존 설계 문서)으로 점검했다. 설계에 영향을 준 사실은 다음과 같다.

- 현재 "AI 에이전트"는 결정론 스코어링 위에 단발 LLM 호출을 얹은 고정 파이프라인이다. 모델이 도구를 스스로 고르는 루프는 관리자 전용 채팅(`app/services/mirofish/chat_agent.py`) 하나뿐이다.
- 평가 표본이 26~32건이라 학습 게이트(100건)가 닫혀 있다. LLM 확신도는 모델의 자기 보고 값이고 실제 적중률과 대조되지 않는다.
- 뉴스와 LLM 출력을 시점별로 저장하지 않아 LLM 계층은 과거 시점으로 재현할 수 없다.
- 10월 이후 추가된 엔진(Kelly, AlphaLab, 수익 기회 엔진, 제갈공명, TOP3 어드바이저) 가운데 비용 차감 후 표본 외 성과가 문서로 확인된 것이 없다. 엔진마다 결과 저장소와 채점 기준이 달라 서로 비교할 수 없다.
- 구독자용 대화·에이전트 화면이 없고, 디자인 토큰 체계가 없다(팔레트 4개 중첩).
- 보안: Stripe 웹훅 시크릿 기본값이 빈 문자열, 스크래퍼 제어 라우트가 Pro 권한뿐, 종목분석 캐시 오염 경로가 있다.

점검 당시 로컬 브랜치는 `origin/main`보다 162커밋 뒤였다. 구현 계획은 `origin/main` 기준으로 세운다.

## 2. 확정된 결정

| 항목 | 결정 |
|---|---|
| 최종 결과물 | 구독자용 리서치 에이전트와 자동 검증 체계를 하나로 묶는다. 에이전트의 모든 판정이 원장에 기록·채점되고, 성적이 에이전트의 기억과 확신도 보정에 다시 쓰인다 |
| 인프라 | miniPC 한 대, Flask, SQLite, Task Scheduler 유지. 프로세스만 웹·워커·스케줄러로 나눈다 |
| LLM 비용 | 배치 우선. 구독자는 배치 실행 기록을 무료로 재생하고, 직접 질문은 등급별 일일 한도 안에서만 실행한다 |
| 판정 형태 | 확률 예측과 근거. 매수/매도 지시, 진입·손절·목표가·비중 제시는 하지 않는다 |
| 접근 방식 | 예측 리그. 기존 엔진과 새 에이전트를 모두 "예측자"로 두고 하나의 원장에서 같은 기준으로 채점한다 |

## 3. 목표와 비목표

**목표**

1. 모든 예측자의 예측을 시점 고정으로 기록하고 자동 채점하는 단일 원장을 만든다.
2. 도구를 스스로 골라 조사하고 확률 예측을 제출하는 리서치 에이전트를 만든다.
3. 구독자가 예측, 추론 과정, 예측자의 과거 성적을 함께 보는 화면을 만든다.

**비목표**

- 자동 매매, 주문 경로, 매매 지시 (상위 문서의 E-게이트 유지).
- 수익 우위의 보장. 원장은 우위의 유무를 측정할 뿐이다.
- 스택 교체(Postgres, Docker, FastAPI 등)와 기존 코드 전면 재작성.
- 기존 엔진의 계산 로직 변경.
- 기존 LLM 접근 계층 4개의 통합, 스케줄러 파일 분해 (§10 별도 과제).

```

종가베팅 V2   ─┐                                           ┌─ 성적표 화면

```

신규 패키지 세 개를 둔다. 서로는 아래 인터페이스로만 통신한다.

| 패키지 | 책임 | 의존 |
|---|---|---|
| `app/services/forecast_league/` | 원장 저장, 제출 검증, 채점, 성적표 집계 | `daily_prices.csv`, `app/utils/paths.py` |
| `app/services/research_agent/` | 추론 루프, 도구, 실행 기록, 기억 조회 | `forecast_league`, `ai_routing`, 기존 MCP 도구 |
| `app/services/league_worker/` | 영속 잡 큐, 배치 실행, 채점 실행 | 위 두 패키지 |

mirofish 패키지는 수정하지 않고, 어댑터가 mirofish의 결과물을 읽어 원장에 제출한다.

## 5. 예측 원장 (`forecast_league`)

### 5.1 저장소

SQLite(WAL) 파일 하나: `data/forecast_league/league.db`.

| 테이블 | 주요 열 | 비고 |
|---|---|---|
| `forecasters` | `forecaster_id`, `version`, `kind`(engine/agent/baseline), `probability_source`(native/derived), `registered_at` | 버전이 바뀌면 새 행 |
| `forecasts` | `forecast_id`, `forecaster_id`, `version`, `stock_code`, `asof_ts`, `event_id`, `probability`, `raw_score`, `capsule_hash`, `source_ref`, `official`(0/1), `created_at` | 추가 전용. (`forecaster_id`,`version`,`stock_code`,`asof_ts`,`event_id`) 유일 |
| `abstentions` | `forecaster_id`, `version`, `stock_code`, `asof_ts`, `reason` | 기권 기록 |
| `capsules` | `capsule_hash`, `payload`(압축 JSON), `created_at` | 내용 해시가 키 |
| `resolutions` | `forecast_id`, `outcome`(0/1), `resolved_at`, `entry_price`, `exit_reason`, `net_return`, `price_source_version` | 예측당 1행 |
| `scorecards` | `forecaster_id`, `version`, `event_id`, `window`, 지표 열, `computed_at` | 채점기가 재계산 |
| `lessons` | `forecast_id`, `tags`, `regime`, `sector`, `text`, `created_at` | §6.4 |
| `agent_run_events` | `run_id`, `seq`, `kind`, `summary`, `tool`, `args`, `result_digest`, `created_at` | §6.3 |
| `jobs` | `job_id`, `kind`, `args`, `status`, `attempts`, `created_at`, `updated_at` | §7 |

### 5.2 표준 사건

예측자 간 비교를 위해 사건 정의를 고정한다. 첫 사건은 기존 가상 매매 엔진(`paper_positions`)과 같다.

- `E1`: 기준일 다음 거래일 시가에 진입했을 때, 8거래일 안에 +8%에 도달한다. 같은 기간에 −7%에 먼저 닿으면 실패. 같은 날 둘 다 닿으면 실패(손절 우선, 기존 규칙과 동일).

사건을 추가할 때는 새 `event_id`로 추가하고 기존 정의는 바꾸지 않는다.

### 5.3 제출 규칙

1. 제출은 프로세스 내부 함수 `submit_forecast()`로만 한다. HTTP 쓰기 경로는 두지 않는다.
2. `created_at`은 서버 시각으로 찍는다. `created_at`이 `asof_ts` 다음 거래일의 장 시작 시각 이후면 거부한다.
3. `asof_ts`가 `created_at`보다 미래이면 거부한다.
4. `probability`는 0.02~0.98로 제한한다. 범위 밖이면 거부한다(잘라내지 않는다).
5. 수정·삭제 함수는 만들지 않는다. 같은 유일 키로 다시 제출하면 거부한다.
6. `capsule_hash`가 가리키는 캡슐이 없으면 거부한다. 기준선 예측자는 입력 수치만 담은 캡슐을 쓴다.

### 5.4 근거 캡슐

예측 시점에 본 자료를 그대로 담는다: 도구 호출과 결과 원문, 뉴스·공시 본문, 수치, 프롬프트 버전, 모델명. 내용의 SHA-256이 키다. 같은 내용은 한 번만 저장된다. 캡슐은 과거 시점 재현과 화면의 "당시 본 원문" 표시에 쓴다.

### 5.5 점수를 확률로 환산

확률을 내지 않는 엔진(종가베팅 17점, 스캐너 점수 등)은 어댑터가 환산한다.

- 그 예측자의 과거 해소된 예측을 점수 구간으로 나누고, 구간별 실제 적중률을 확률로 쓴다.
- 환산에는 `asof_ts` 이전에 해소된 표본만 쓴다.
- 구간 표본이 30건 미만이면 그 예측자의 전체 적중률을, 전체도 30건 미만이면 전 예측자 기저율을 쓴다.
- `probability_source='derived'`로 표시하고 `raw_score`를 함께 저장한다.

### 5.6 기준선 예측자

우위는 기준선을 이기는 것으로 정의한다. 두 개를 항상 등록한다.

- `baseline_base_rate`: 모든 후보에 직전 250거래일 `E1` 기저율을 낸다.
- `baseline_momentum`: 20일 수익률 순위를 5.5 방식으로 환산한 확률을 낸다.

기준선은 다른 예측자가 예측을 낸 종목 전체에 대해 같은 날 예측을 낸다.

### 5.7 채점

장 마감 후 워커가 실행한다.

- 가격 출처는 `data/daily_prices.csv` 하나다. 채점 시 사용한 파일의 수정 시각과 행 수를 `price_source_version`에 남긴다.
- 지표: Brier 점수, 로그 손실, 확률 구간별 적중률(보정 곡선), 상위 K개 정밀도, 평균 순수익(왕복 비용 0.23% 차감, 기존 `costs.py` 사용), 진입일 블록 부트스트랩 95% 신뢰 구간, 기준선 대비 차이.
- 해소된 예측이 100건 미만인 예측자는 지표 대신 `insufficient`를 기록한다.
- 채점은 멱등이다. 같은 예측을 다시 채점해도 결과가 같고 행이 늘지 않는다.

**선행 확인 사항:** `origin/main`의 `docs/alpha_reliable_top3_research_2026_11_10.md`에 "KIS 일봉이 장후 가격과 섞인다"는 미해결 문제가 있다. 1단계 구현 계획의 첫 작업으로 `daily_prices.csv`의 시가·고가·저가가 정규장 값인지 표본 대조로 확인한다. 섞여 있으면 채점 전에 가격 출처부터 고친다.

### 5.8 조회 API

모두 GET, `@pro_required`, `Cache-Control: private`.

| 경로 | 내용 |
|---|---|
| `/api/league/forecasts?date=` | 그날의 공식 예측 목록 |
| `/api/league/forecasts/<forecast_id>` | 예측 상세와 해소 결과 |
| `/api/league/capsules/<hash>` | 근거 캡슐 |
| `/api/league/scorecards` | 예측자별 성적표 |

## 6. 리서치 에이전트 (`research_agent`)

### 6.1 실행 단계

`chat_agent.py`의 function calling 루프를 출발점으로 삼는다.

1. **계획**: 확인할 항목을 정한다.
2. **조사**: 읽기 전용 도구를 골라 호출하고 결과를 보고 다음 조회를 정한다. 도구 호출 상한과 비용 상한을 실행마다 둔다(수치는 3단계 구현 계획에서 DeepSeek 단가로 산정).
3. **반대 근거 수집**: 가설을 깨는 근거를 찾는 도구 호출이 1회 이상 있어야 한다. 없으면 제출을 거부한다.
4. **제출**: `E1` 확률, 핵심 근거 3~5개(각각 캡슐 내 도구 결과를 가리킴), 반대 근거, 판단을 바꿀 조건을 JSON으로 낸다.

제출 전 검증: 스키마 검증, `number_guard`로 답변 속 수치와 도구 결과 대조. 검증 실패, 한도 초과, 도구 실패 시 예측을 내지 않고 `abstentions`에 사유와 함께 기록한다.

### 6.2 도구

- `app/services/mirofish/mcp_server.py`와 `graphrag/mcp_tools.py`의 도구 중 읽기 전용만 등록한다. 쓰기 도구는 등록하지 않는다.
- 모든 도구는 `asof` 인자를 받아 그 시각 이후 데이터를 반환하지 않는다. `asof`를 지원하지 않는 도구는 감싸서 지원하게 하거나 등록에서 뺀다. 대상 도구 수는 3단계 구현 계획에서 센다.
- 원장 도구 세 개를 추가한다: 종목 노트(같은 종목의 과거 예측과 결과), 기저율(조건별 과거 적중률), 교훈 조회.
- 도구 결과는 프롬프트에서 "신뢰할 수 없는 데이터" 구획으로 감싼다.

### 6.3 실행 기록

단계마다 이벤트(순번, 종류, 추론 요약, 도구명, 인자, 결과 요약)를 `league.db`의 `agent_run_events`에 저장한다. 조회는 `GET /api/league/runs/<run_id>/events?after=<순번>`으로, 클라이언트가 마지막 순번부터 이어 받는다. 한 요청은 30초 안에 응답하므로 터널의 100초 한계와 무관하다. 조사 단계의 도구 결과 전체가 그 실행의 근거 캡슐이 된다.

### 6.4 기억

벡터 저장소는 쓰지 않는다. 원장이 기억이다.

- **종목 노트**: `forecasts`와 `resolutions`를 종목으로 조회.
- **교훈**: 예측이 해소되면 워커가 사후 분석을 생성해 `lessons`에 저장한다. 확률 0.7 이상으로 틀렸거나 0.3 이하로 맞은 경우만 대상이다. 조회는 업종, 태그, 시장 국면의 정확 일치로 한다.
- **기저율**: `resolutions`의 집계.

교훈과 기저율 조회도 `asof` 이전에 해소된 것만 반환한다.

### 6.5 확신도 보정

에이전트의 원래 확률을 구간별 실제 적중률로 보정한다(§5.5와 같은 방식, 시점 이전 표본만). 해소 표본 100건 미만이면 보정하지 않고 "보정 전"으로 표시한다. 원장에는 원래 확률을 저장하고, 보정 확률은 조회 시 계산해 둘 다 반환한다.

### 6.6 배치와 구독자 질문

- **배치(공식)**: 종가베팅 실행 직후와 장 마감 후, 그날 검출 후보 상위 N종목(초기 N=10, 비용 산정 후 조정)을 실행한다. `official=1`로 기록하고 성적표에 반영한다.
- **구독자 질문**: 등급별 일일 횟수 안에서 실행한다. 그날 배치 예측이 있는 종목은 새 확률을 내지 않고 배치 예측과 캡슐을 근거로 답한다.
- **배치에 없는 종목**: 한도 안에서 실행하고 `official=0`으로 기록한다. 성적표에는 반영하지 않는다.
- 일일 횟수는 기존 구독자 런 한도 구조를 따르고, 수치는 4단계 구현 계획에서 정한다.

### 6.7 버전

모델명, 프롬프트, 도구 목록 중 하나라도 바뀌면 `version`을 올려 새 예측자로 등록한다. LLM 호출은 `app/services/ai_routing/`으로만 한다.

## 7. 워커 (`league_worker`)

- Flask와 별도 프로세스로 실행한다(`python -m app.services.league_worker`). miniPC에는 기존 방식대로 SYSTEM 계정 Task와 워치독을 등록한다.
- 잡은 `league.db`의 `jobs` 테이블에 저장한다: 종류, 인자, 상태(queued/running/done/failed), 시도 횟수, 시각. 재시작 시 `running`으로 남은 잡은 `queued`로 되돌린다.
- 잡 종류: 어댑터 수집, 에이전트 배치 실행, 구독자 질문 실행, 채점, 교훈 생성.
- `scheduler.py`에는 잡을 큐에 넣는 호출만 등록한다. 로직은 넣지 않는다.
- Flask의 구독자 질문 라우트는 잡을 넣고 202와 `run_id`를 반환한다(기존 `decision_jobs.py` 패턴).

## 11. 오류 처리

| 상황 | 동작 |
|---|---|
| 어댑터가 엔진 결과물을 읽지 못함 | 그 예측자만 그날 건너뛰고 워커 로그와 개인봇 알림. 다른 예측자는 계속 |
| LLM 전부 실패 또는 예산 소진 | 기권 기록. 예측을 만들지 않음 |
| 도구 실패 | 그 도구 결과 없이 계속하되, 근거가 3개 미만이면 기권 |
| 채점 시 가격 누락(거래정지 등) | 해소를 보류하고 다음 채점 때 재시도. 20거래일 넘으면 `void`로 표시하고 지표에서 제외 |
| 워커 중단 | 워치독이 재기동. `running` 잡은 `queued`로 복구 |
| `league.db` 잠금 | WAL과 짧은 재시도. 실패하면 잡 실패로 기록 후 재시도 |

텔레그램 알림은 시스템 메시지이므로 개인봇으로만 보낸다.

## 12. 테스트

- **원장**: 늦은 제출 거부, 미래 `asof_ts` 거부, 중복 거부, 범위 밖 확률 거부, 수정·삭제 함수 부재(모듈 공개 이름 검사).
- **미래 정보 차단**: 환산·보정·기저율·교훈이 `asof` 이후 표본을 쓰지 않음을 합성 데이터로 검증.
- **채점**: `E1`의 익절, 손절, 같은 날 양쪽 도달, 기간 만료 사례. 멱등성. CIO SELL 청산이 없는 사례에서 `paper_positions`와 같은 입력에 같은 결과(`E1`에는 CIO SELL 청산이 없다).
- **에이전트**: LLM을 스텁으로 바꾼 결정론 실행. 반대 근거 단계 없으면 제출 거부. `number_guard` 불일치 시 기권. 도구 결과 속 지시문이 제출 내용을 바꾸지 못함.
- **도구**: 등록된 모든 도구가 `asof`를 지키는지 계약 테스트.
- **과거 시점 재현**: 저장된 캡슐로 같은 실행을 다시 돌려 같은 제출이 나오는지 확인(LLM 응답은 캡슐에 저장된 값 사용).
- **API**: 비로그인과 비구독자 거부, 쓰기 메서드 405.
- **보안 0단계**: 빈 시크릿 웹훅 거부, Pro 계정의 스크래퍼 제어 403, 조작된 `name`이 캐시에 남지 않음.
- **프론트**: 새 화면의 가드, 표본 부족 시 "판정 불가" 표시, 이벤트 이어 받기.

## 13. 단계와 완료 기준

단계마다 별도 구현 계획을 세운다. 완료는 miniPC 배포와 운영 확인까지다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 0 | 보안 선행 수정 3건 | §12 보안 테스트 통과, miniPC 반영 |
| 1 | 원장, 채점기, 기준선 예측자, 워커 | §12 원장·채점 테스트 통과, 기준선의 채점 결과가 운영에서 생성 |
| 2 | 기존 엔진 어댑터, 성적표 화면, 디자인 토큰과 공용 컴포넌트 | 엔진 3개 이상이 매일 예측 제출, 성적표가 구독자 계정에 표시 |
| 3 | 리서치 에이전트 배치 실행 | 배치 예측이 원장에 기록, 과거 시점 재현 테스트 통과 |
| 4 | 오늘의 예측, 리서치 실행 보기, 구독자 질문 | 구독자 계정으로 재생과 한도 내 질문 동작 |
| 5 | 확신도 보정 표시, 교훈 기억, 예측자 가중치 | 해소 표본 100건 도달 후 보정 확률 표시 |

2단계 어댑터의 첫 대상은 종가베팅 V2, 알파 스캐너, CIO 판정이다. 제갈공명과 AlphaLab은 `origin/main` 코드를 확인한 뒤 2단계 구현 계획에서 포함 여부를 정한다.

## 14. 알려진 한계

- 원장은 어떤 예측자에도 우위가 없다는 결과를 낼 수 있다. 그 경우 5단계의 가중치는 쓰지 않고, 상품 가치는 검증 과정이 투명한 리서치에 둔다.
- 해소 표본 100건에 도달하는 시점은 1단계에서 하루 예측 수를 확인한 뒤에야 추정할 수 있다.
- `E1` 하나로는 예측자의 모든 강점을 재지 못한다. 사건 추가는 `E1` 표본이 쌓인 뒤 검토한다.
- 환산 확률(§5.5)은 초기에 기저율과 거의 같아 예측자 간 차이가 작게 보인다.
- 에이전트 실행당 비용과 `asof` 미지원 도구 수는 아직 측정하지 않았다.
