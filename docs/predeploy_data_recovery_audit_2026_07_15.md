# MarketFlow 배포 전 데이터·복구 감사 (2026-07-15)

## 결론

감사 시작 시점의 배포/재시작 판정은 **NO-GO**였다.

운영 회원 DB의 SQLite 무결성 검사와 회원·구독 관계는 정상이며, 현재 권한 만료 드리프트도 발견되지 않았다. 최초 점검에서는 MarketFlow 회원 DB의 검증된 백업과 복구 리허설이 확인되지 않아 배포를 차단했다. 운영자 승인 후 아래의 사전 조치를 완료해 데이터 복구 게이트를 통과했다.

초기 감사는 운영 데이터를 변경하지 않는 읽기 전용 점검으로 수행했다. 이후 승인된 사전 조치는 백업 생성과 ACL 보강으로 한정했으며, 회원·구독·게시물 레코드는 변경하지 않았다. 감사 보고에는 이메일, 이름, 비밀번호 해시, 게시물 내용, 업로드 파일명 등 개인정보와 민감값을 포함하지 않았다.

## P0 재시작 차단 항목

1. **회원 DB 복구본 부재**
   - `data/users.db`는 존재하고 `PRAGMA quick_check=ok`다.
   - 알려진 MarketFlow 백업 경로와 예약 작업에서 `users.db`의 일관된 백업을 찾지 못했다.
   - 기존 `BitMan-JustBuy-AuxBackup` 작업은 다른 프로젝트용이며 MarketFlow를 보호하지 않는다.
   - SQLite가 WAL 모드이므로 서비스 실행 중 `users.db` 파일만 단순 복사해서는 일관된 복구본을 보장할 수 없다.

2. **운영 `SECRET_KEY` 영속 설정 부재**
   - MiniPC 운영 환경 검사 결과 `SECRET_KEY_CONFIGURED=0`이다.
   - 보안 강화 코드 배포 후 영속 키를 새로 설정하면 기존 로그인 토큰은 무효화되어 전 사용자 재로그인이 필요하다.
   - 회원·구독 데이터는 삭제되지 않지만 사용자 영향이 있으므로 배포 공지와 함께 적용해야 한다.

3. **운영 `.env` ACL 보강 필요**
   - `.env`는 존재하지만 광범위한 그룹 쓰기를 허용하는 ACL 규칙 1건이 탐지됐다.
   - 비밀값을 출력하지 않은 상태로 파일 소유자와 서비스 계정 중심으로 쓰기 권한을 축소해야 한다.

## 안전한 배포 전 절차

### 1. 일관된 백업 생성

1. SQLite 온라인 백업 API로 `users.db`의 시점 일관 백업을 타임스탬프 디렉터리에 생성한다.
2. 백업본에서 `quick_check=ok`를 확인한다.
3. 핵심 테이블 수를 운영본과 비교한다. 최소한 회원 246, 구독 202, 게시물 160이 일치해야 한다.
4. 외래키 위반은 알려진 `post_images` 60건과 동일해야 하며 신규 위반이 없어야 한다.
5. 백업본을 별도 임시 경로로 복원해 읽기 전용 검사와 인증/관리 조회 스모크 테스트를 수행한다.
6. 커뮤니티 업로드(약 323 MB), MiroFish 워크플로우(약 76 MB), 보안 ACL을 유지한 `.env`와 운영 스크립트를 함께 보존한다.

### 2. 비밀키와 ACL

1. 충분히 긴 무작위 `SECRET_KEY`를 MiniPC `.env`에 영속 설정한다.
2. `.env` 쓰기 권한을 소유자/서비스 계정으로 제한한다.
3. 기존 로그인 토큰 무효화와 재로그인 필요성을 운영 공지에 포함한다.

### 3. 소스 배포

1. 코드만 의도적으로 커밋하고 `data/`, `logs/`, 토큰, SQLite WAL/SHM, 업로드를 스테이징하지 않는다.
2. MiniPC에서는 `git pull --ff-only` 또는 명시적 파일 배포를 사용한다.
3. `force_sync_and_restart.ps1`의 `git reset --hard` 방식은 이번 배포에 사용하지 않는다.
4. 최종 전환 직전에만 Flask와 관련 스케줄러를 순서대로 정지/재시작한다.

### 4. 재시작 후 검증

1. 로컬 `/healthz`, `/api/health` 확인
2. 공개 `https://marketflow-api.bit-man.net/healthz`와 `/api/health` 확인
3. 로그인, `/api/auth/me`, 구독 상태, 관리자 회원/구독 조회 확인
4. 회원·역할·상태·등급·구독 집계를 재검사해 배포 전 수치와 비교
5. `quick_check` 및 외래키 위반 수 재검사
6. 서머리 브리핑, VCP/W 패턴, AI Brain, 주식 분석, 커뮤니티, MiroFish, 종가베팅 V2, 스케줄러 하트비트 확인

## 롤백 원칙

- 이번 변경에는 파괴적 DB 마이그레이션이 없으므로 장애 시 먼저 **소스만 롤백**한다.
- DB 백업 복원은 DB가 실제로 손상됐을 때만 수행한다. 그렇지 않으면 배포 이후 생성된 회원/구독/게시물 데이터를 잃을 수 있다.
- DB 복원이 필요하면 Flask와 DB 쓰기 작업을 정지하고 검증된 일관 백업을 복원한 뒤 WAL/SHM을 복구 절차에 맞게 처리한다. 이후 `quick_check`, 레코드 수, 인증 스모크 테스트를 통과해야 서비스를 연다.
- 업로드와 워크플로우는 DB와 별도로 복원 가능하도록 보존한다.
